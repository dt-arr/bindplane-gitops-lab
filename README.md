# BindPlane GitOps Lab

Demonstrates managing OTel collector configuration through Git using BindPlane as the distribution layer. Covers two configuration models: **raw OTel YAML** and **BindPlane modular (component) configs**, with round-trip proof between Git, the BindPlane UI, and a live collector via OpAMP.

---

## Two configuration models

| | Raw OTel | Modular (Component) |
|---|---|---|
| **Format** | Standard OTel YAML wrapped in a BindPlane manifest | BindPlane typed sources/destinations |
| **UI view** | YAML editor only | Visual pipeline builder |
| **What runs on collector** | Exactly what you wrote | OTel YAML generated by BindPlane |
| **Use when** | You own the OTel pipeline fully | You want BindPlane abstractions and UI editing |
| **Round-trip fidelity** | OTel content is byte-identical | 3 metadata fields added on export |

### Why you can't use BindPlane source types in raw OTel

BindPlane source types (e.g. `bindplane-agent`, `syslog`, `windowsevents_v3`) are server-side abstractions. BindPlane expands them into real OTel components (`filelog`, `prometheus`, etc.) based on the collector's platform and component versions. A raw OTel YAML file must only contain real OTel component names — the collector process rejects anything else.

## Prerequisites

- BindPlane CLI installed (`bindplane` on PATH or at `%LOCALAPPDATA%\Programs\Bindplane\bindplane.exe`)
- A BindPlane Cloud account and project
- A running collector agent registered to the project

### Set up CLI profile

```powershell
bindplane profile set <PROFILE_NAME> \
  --remote-url https://app.bindplane.com \
  --api-key <YOUR_API_KEY>
```

Verify:
```powershell
bindplane get configurations --profile <PROFILE_NAME>
```

## Repository layout

```
bindplane/
  baseline/       # Exported as-is from BindPlane — the source of truth after a round-trip
  lab/            # Working files you edit in Git and apply to BindPlane
  generated-otel/ # Raw OTel YAML generated by BindPlane (what the collector actually runs)
scripts/
  Use-LabCli.ps1  # Dot-source to add CLI to PATH in the current session
docs/
```

> Never commit API keys, collector IDs, or enrollment secrets. Exports can contain credentials — review before tracking.

## Workflow: Git → BindPlane → Collector

```
Edit YAML in Git
      │
      │  bindplane apply -f <file> --profile <profile>
      ▼
BindPlane Cloud (new config version, no rollout yet)
      │
      │  bindplane rollout start <config-name> --profile <profile>
      ▼
Collector receives config via OpAMP
```

## Workflow: BindPlane UI → Git

```
Edit config in BindPlane UI
      │
      │  bindplane get configurations <name> --export -o yaml --profile <profile>
      ▼
Review diff, sanitize, copy to bindplane/baseline/
      │
      │  git add / git commit
      ▼
Git holds the updated state
```

## Model 1 — Raw OTel YAML

Use this when you want full control over the OTel pipeline and don't need BindPlane's component abstractions.

### Manifest format

`bindplane/lab/gitops-lab-raw-config.yaml`

```yaml
apiVersion: bindplane.observiq.com/v1
kind: Configuration
metadata:
  name: gitops-lab-raw-config
  labels:
    platform: linux
    agent-type: bindplane-otel-collector
spec:
  contentType: raw
  raw: |
    receivers:
      filelog/agent-logs:
        include:
          - ${OIQ_OTEL_COLLECTOR_HOME}/log/collector.log
        start_at: end
    exporters:
      nop:
    service:
      pipelines:
        logs:
          receivers: [filelog/agent-logs]
          exporters: [nop]
  selector:
    matchLabels:
      configuration: gitops-lab-raw-config
```

**Key points:**
- `contentType: raw` tells BindPlane to store and deliver this YAML unchanged
- `spec.raw` contains standard OTel YAML — receivers, processors, exporters, service
- The selector label **must** match the configuration name (BindPlane enforces this)
- The UI shows a plain YAML editor, not the visual pipeline builder

### Apply and roll out

```powershell
bindplane apply -f bindplane/lab/gitops-lab-raw-config.yaml --profile <profile>

# Move a collector onto this config
bindplane label agent <AGENT_ID> configuration=gitops-lab-raw-config --overwrite --profile <profile>

bindplane rollout start gitops-lab-raw-config --profile <profile>
bindplane rollout status gitops-lab-raw-config --profile <profile>
```

### Export (round-trip back to Git)

```powershell
bindplane get configurations gitops-lab-raw-config --export -o yaml --profile <profile>
```

BindPlane adds three fields on export — include them in your tracked file so future diffs are clean:
```yaml
spec:
  measurementInterval: ""
  topologyInterval: ""
  disableLegacyEnvVarNormalization: false
```
The raw OTel content itself comes back byte-identical.

### View what the collector actually receives

```powershell
bindplane get configurations gitops-lab-raw-config -o raw --profile <profile>
```

For raw configs this is identical to `spec.raw`. For modular configs it shows the full generated OTel — useful for debugging.

## Model 2 — Modular (component) config

Use this when you want the BindPlane visual pipeline UI, managed component abstractions, and platform-aware OTel generation.

### Manifest format

`bindplane/lab/gitops-lab-agent-config.yaml`

```yaml
apiVersion: bindplane.observiq.com/v2
kind: Configuration
metadata:
    name: gitops-lab-agent-config
    labels:
        agent-type: observiq-otel-collector
        platform: windows
spec:
    sources:
        - displayName: Bindplane Agent
          type: bindplane-agent
          parameters:
            - name: telemetry_types
              value:
                - Logs
                - Metrics
            - name: log_path
              value: log/collector.log
            - name: start_at
              value: end
          routes:
            logs:
                - id: "0"
                  components:
                    - destinations/d-null-destination
            metrics:
                - id: "0"
                  components:
                    - destinations/d-null-destination
    destinations:
        - id: d-null-destination
          name: null-destination
    selector:
        matchLabels:
            configuration: gitops-lab-agent-config
```

**Key points:**
- Uses `apiVersion: v2` and named source types from BindPlane's component library
- `type: bindplane-agent` is a BindPlane abstraction — not a real OTel receiver
- BindPlane generates the underlying OTel YAML and adapts it per collector platform/version
- The UI renders a visual pipeline with tiles and routing lines
- `routes` wire each source signal type to destination components
- Destination `id: d-null-destination` is the internal reference; `name` is the resource name

### Apply and roll out

```powershell
bindplane apply -f bindplane/lab/gitops-lab-agent-config.yaml --profile <profile>

bindplane label agent <AGENT_ID> configuration=gitops-lab-agent-config --overwrite --profile <profile>

bindplane rollout start gitops-lab-agent-config --profile <profile>
bindplane rollout status gitops-lab-agent-config --profile <profile>
```

### Export after UI edit

```powershell
bindplane get configurations gitops-lab-agent-config --export -o yaml --profile <profile>
```

The export is in the same v2 modular format. Source IDs (server-assigned ULIDs) are included — keep them in the tracked file so re-applying updates the existing sources rather than creating duplicates.

## Key CLI reference

| Purpose | Command |
|---|---|
| List configurations | `bindplane get configurations --profile <profile>` |
| List agents | `bindplane get agents --profile <profile>` |
| Apply a manifest | `bindplane apply -f <file> --profile <profile>` |
| Export a config | `bindplane get configurations <name> --export -o yaml --profile <profile>` |
| Get generated OTel | `bindplane get configurations <name> -o raw --profile <profile>` |
| Relabel an agent | `bindplane label agent <AGENT_ID> <key>=<value> --overwrite --profile <profile>` |
| Start rollout | `bindplane rollout start <config-name> --profile <profile>` |
| Check rollout status | `bindplane rollout status <config-name> --profile <profile>` |
| List available source types | `bindplane get source-types --profile <profile>` |

## Round-trip summary

```
bindplane/lab/<config>.yaml   ← you edit this
        │  bindplane apply
        ▼
BindPlane Cloud (versioned)
        │  bindplane rollout start
        ▼
Collector (via OpAMP)
        │  edit in UI, then:
        │  bindplane get configurations <name> --export -o yaml
        ▼
bindplane/baseline/<config>.yaml   ← reviewed export, committed to Git
```

The `baseline/` files represent what BindPlane currently holds. The `lab/` files are what you author and apply. After a UI edit, export into `baseline/` and `git diff` shows exactly what changed.
